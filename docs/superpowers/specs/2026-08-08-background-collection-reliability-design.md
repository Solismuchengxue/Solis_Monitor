# Solis Monitor 后台采集可靠性加固设计

- 日期：2026-08-08
- 状态：已批准；实施、部署、推送与 Release 更新仍需分别授权
- 基线提交：`e873ad784fc01c9d0f1689b7ee730a7a9b6d6bae`

## 背景

Solis Monitor 曾因 Codex 本地 JSONL 中出现 `payload.info = null` 的不完整
`token_count` 事件，在指标定时器线程抛出未处理的
`InvalidOperationException`，最终终止整个 WPF 进程。直接 EXE 与安装包使用同一
载荷，因此表现一致。

当前修复已经在 JSON 读取边界过滤该事件。本设计继续补强两个后台采集定时器，
使普通采集异常不会结束主程序，同时保证故障可见、可调查、可自动恢复，并为日志
和内存设定硬上限。

## 目标

1. 指标和天气采集发生普通托管异常时，主程序继续运行。
2. 保留最后一次完整有效数据，不发布半成品快照。
3. 继续使用原有采集周期自动重试，成功后自动恢复诊断状态。
4. 在本机保存最少、脱敏且有硬上限的错误证据。
5. 补齐 Codex 会话首行根节点和 `payload` 的 JSON 类型边界。
6. 以失败优先的回归测试证明隔离、恢复、限流、轮转和脱敏行为。

## 非目标

- 不增加全局未处理异常处理器。
- 不隔离启动、UI、硬件初始化、设备发现、OTA 或通知模块的异常。
- 不改变 Timer 周期、设备协议、固件、UI 布局或用户配置格式。
- 不弹出 Windows 故障通知。
- 不引入第三方日志依赖或通用任务调度框架。
- 不在本阶段部署、推送或更新 GitHub Release。

## 方案选择

采用共享后台采集保护器，而不是在两个回调中复制 `try/catch`，也不采用全局异常
兜底。共享保护器只执行一次采集并处理失败，不拥有 Timer，不改变调度和生命周期。

该方案比重复 `catch` 多两个小型、职责单一的组件，但异常分类、日志限流和测试入口
保持一致；同时避免把可靠性加固扩展成通用后台框架。

## 组件与职责

### `BackgroundCollectionGuard`

- 接收固定模块标识、采集操作和故障回调。
- 成功时正常返回，不保留历史状态。
- 捕获普通托管异常，先尝试写入脱敏日志，再调用诊断故障回调。
- 日志写入失败不得阻止诊断更新，也不得逃出保护器。
- 不捕获 `OutOfMemoryException`、`AccessViolationException` 等严重进程状态异常。
- 不缓存异常对象、采集结果或待写日志队列。

### `RuntimeErrorLog`

- 日志路径为
  `%LocalAppData%\SolisMonitor\logs\runtime-errors.log`，实际根目录沿用
  `SolisRuntime.SettingsDirectory`。
- 每行只包含 UTC 时间、固定模块名、异常类型和 HResult，例如：

  ```text
  2026-08-08T12:30:00.0000000Z|metrics|System.InvalidOperationException|0x80131509
  ```

- 不记录异常消息、堆栈、Codex 行内容、API Key、设备令牌、Wi-Fi 信息或完整路径。
- 单行字段按固定长度截断，禁止换行注入。
- 当前文件上限 512 KiB；写入将越界时，将当前文件替换为唯一备份
  `runtime-errors.log.1`。
- 当前文件和一个备份的总上限约 1 MiB，不保留更多历史文件。
- 相同模块和异常类型五分钟内最多写入一次。
- 指标与天气分别只保存一个最近写入签名和时间；内存状态数量固定。
- 不保持文件流，不使用后台写入队列。并发写入通过一个短生命周期锁串行化。
- 目录创建、打开、写入或轮转失败时静默降级，不递归记录日志错误。

### `SolisRuntime`

- 保留现有 `_metricsUpdateRunning` 和 `_weatherUpdateRunning` 防重入门。
- 仅把 `UpdateMetrics` 和 `UpdateWeather` 中的采集主体交给保护器。
- `finally` 仍负责释放防重入状态，关闭流程和 Timer 生命周期不变。
- 指标采集失败时不发布快照，保留最后完整快照；连续五秒没有新快照时，复用
  现有“PC 指标服务／指标快照未更新”诊断。下一次成功发布后自动恢复。
- 天气采集失败时保留最后有效天气数据，并把天气诊断标记为
  `BackgroundCollectionError`；下一次成功的 `ObserveWeather` 自动恢复。
- 故障不会触发 Windows 通知。

### `SolisDiagnosticsMonitor`

- 增加天气后台采集失败入口，使用固定、脱敏的状态文字和错误类别。
- 保留最近正常时间，不保存异常对象或故障历史集合。
- 不新增诊断卡片或 UI 字段。
- 指标采集继续复用现有快照新鲜度检查，避免新增不准确的诊断来源。

### `CodexLocalWeeklyUsageReader`

- `IsSubagentSession` 在调用 `TryGetProperty` 前检查根节点为 Object。
- 检查 `payload` 为 Object 后再读取 `source`。
- 会话首行为数组、字符串、数字、`null` 或 `payload:null` 时返回非子代理结果，
  不抛出 `InvalidOperationException`。
- 非法记录不会改变 Token 计算规则，也不会输出原始内容。

## 数据流与恢复

### 指标采集

1. 每秒 Timer 进入原有防重入门。
2. 保护器执行网络和 Codex 指标读取。
3. 全部成功后发布一个完整快照。
4. 普通异常时保留旧快照，按限流规则写日志并结束本周期。
5. 连续五秒无新快照时，现有诊断逻辑显示指标快照未更新。
6. 后续周期继续执行；首次成功发布后恢复新鲜状态。

### 天气采集

1. 每分钟 Timer 进入原有防重入门。
2. 保护器执行天气读取。
3. 成功时更新天气快照和现有天气诊断。
4. 普通异常时保留旧天气数据，按限流规则写日志并标记天气诊断故障。
5. 后续周期继续执行；首次成功读取后恢复正常。

### 日志失败

日志属于辅助证据，不是采集成功的前置条件。日志目录不可写、文件被占用或轮转失败
时，保护器仍执行诊断故障回调并正常结束本周期；日志错误本身不会再次写日志。

## 资源与隐私上限

| 项目 | 硬上限或规则 |
| --- | --- |
| 当前日志 | 512 KiB |
| 备份日志 | 512 KiB，最多一个 |
| 总磁盘占用 | 约 1 MiB，加一条定长记录的瞬时余量 |
| 限流状态 | 指标、天气各一个固定槽位 |
| 内存历史 | 不保存历史列表、队列或异常对象 |
| 重复写入 | 相同模块和异常类型五分钟最多一次 |
| 敏感数据 | 不记录消息、堆栈、输入内容、凭据或完整路径 |

即使异常持续数天，磁盘文件数量、磁盘总量和内存状态数量也不会持续增长。

## 测试设计

实施按 RED → GREEN 顺序进行，至少覆盖：

1. 普通采集异常不会逃出保护器，故障回调执行一次。
2. 下一次采集成功可以继续执行，并恢复对应诊断状态。
3. `OutOfMemoryException` 和 `AccessViolationException` 不被普通保护器吞掉。
4. 相同模块和异常类型在五分钟内只写一次。
5. 指标与天气的限流状态互不干扰且状态数量固定。
6. 日志轮转后只有当前文件和一个备份，总量符合约 1 MiB 硬上限。
7. 日志内容不包含异常消息、堆栈、测试输入、凭据样例或完整路径。
8. 日志目录不可写或写入失败时，保护器仍完成故障回调且不抛出普通异常。
9. Codex 首行为数组、字符串、`null` 和 `payload:null` 时不会终止读取。
10. 指标连续失败保留旧快照并由现有五秒新鲜度规则标记故障。
11. 天气失败保留旧数据，下一次成功后恢复诊断状态。
