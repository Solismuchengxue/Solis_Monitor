# Solis Monitor 架构决策

> 状态：当前已落地决策
> 更新日期：2026-07-25

## 1. 文档边界

本文记录已经影响多个模块、具有长期维护成本或存在明确替代方案的架构决定。它不替代根目录 `DESIGN.md`，也不记录任务状态、临时缺陷和逐次调试过程。

每项决策包含：

- **状态**：当前是否仍生效；
- **背景**：为什么必须作出选择；
- **决定**：项目采用的方案；
- **未采用方案**：已评估但没有采用的主要替代项；
- **影响**：该选择带来的收益、限制和维护责任；
- **复审条件**：出现什么变化时应重新评估。

## DEC-001：复用 Libre Hardware Monitor 硬件采集

**状态：已采用**

**背景**
PC 端需要 CPU、GPU、显存、内存、硬盘和传感器数据，并需要兼容 Windows 上不同硬件与驱动。

**决定**
保留 Libre Hardware Monitor 的开源硬件访问内核和原始传感器树，在同一进程内增加 `Solis` 业务层、单设备控制中心、统一快照和 Device API。上游源码、命名空间、程序集及 MPL-2.0 版权信息继续保留。

**未采用方案**

- 从零实现 Windows 硬件传感器访问；
- 继续维护独立 Python 或 C# Agent，再通过 LHM Web 服务二次采集；
- 删除上游界面和未在普通控制中心显示的能力。

**影响**

- 复用已经验证的硬件兼容性，避免重复造轮子；
- 普通用户只看到 Solis 外壳，开发者模式仍能进入完整传感器树；
- 修改上游区域时必须保持许可证、双目标构建和后续合并边界。

**复审条件**
LHM 停止维护、许可证变化、目标硬件无法支持，或出现兼容性更好且迁移成本合理的成熟替代方案。

## DEC-002：PC 端定位为单设备控制中心

**状态：已采用**

**背景**
小屏已经承担实时指标展示，PC 端如果复制同一套卡片，只会增加界面和维护成本。

**决定**
PC 普通界面只管理一台副屏，承担设备向导、配对、显示与电源设置、服务状态、天气配置、启动与托盘、诊断和固件更新。CPU/GPU/Codex 数据看板只保留在副屏和开发者传感器树中。

**未采用方案**

- 在 PC 端复制小屏仪表盘；
- 加入历史趋势和 Codex 用量管理；
- 首版支持多设备分组与批量控制。

**影响**

- 普通界面职责清晰，减少重复信息；
- 当前配对记录和通知模型都以单设备为前提；
- 若未来支持多设备，需要重新设计存储、发现、通知和 OTA 目标选择。

**复审条件**
明确出现同时管理两台以上副屏的真实需求。

## DEC-003：使用 ESP-IDF 与轻量自绘 RGB565 UI

**状态：已采用**

**背景**
硬件为 ESP32-S3-WROOM-1-N8R2，2 MiB PSRAM，界面固定为两个 800×480 页面和少量特殊模式。

**决定**
固件使用 ESP-IDF；显示层由静态 RGB565 背景、裁剪字库、RGBA565 图标、动态文字和脏矩形组成，不引入 LVGL。

**未采用方案**

- Arduino + PlatformIO 作为正式主线；
- LVGL 或其他完整 GUI 框架；
- 浏览器式 UI 或整帧从 PC 传输。

**影响**

- 内存、刷新范围和依赖更可控；
- 静态卡片与动态字段必须同步维护；
- 新增字符要更新裁剪字库，复杂动画和自适应布局的开发成本较高。

**复审条件**
页面数量、交互复杂度或动画需求显著增长，并且经过内存与许可证评估后自绘成本高于成熟框架。

## DEC-004：PC 到副屏使用 1 Hz HTTP 完整快照

**状态：已采用**

**背景**
指标更新频率为每秒一次，数据量小，断线恢复和调试可观察性比低延迟推送更重要。

**决定**
ESP32 每秒通过 HTTP `GET /api/v1/metrics` 拉取 schema 1 完整快照。PC 在同一周期内统一提交硬件、网络、Codex 和天气值，副屏事务性解析。

**未采用方案**

- WebSocket 持续推送；
- 每种指标使用独立接口；
- UDP 广播指标；
- PC 主动向设备推送整帧。

**影响**

- 请求、超时、缓存和恢复行为简单明确；
- 1 Hz 延迟满足副屏用途，但不适合高频动画或电竞级采样；
- 完整快照必须保持 4096 字节响应上限和 schema 1 兼容规则。

**复审条件**
出现必须低于 1 秒延迟、数据规模超出上限或需要多设备高效推送的真实需求。

## DEC-005：设备发现使用物理触发和 6 位配对码

**状态：已采用**

**背景**
副屏日常只供电，用户不应手工填写 Windows IPv4、端口或长令牌；同时需要避免局域网中的设备在未授权时被 PC 自动接管。

**决定**
用户双击 GPIO21 后设备进入发现模式，显示每 60 秒刷新的 6 位配对码。PC 设备向导只列出处于发现模式的设备；用户选择设备并输入配对码后，双方自动同步 PC IPv4、固定端口 18472 和内部设备令牌。

**未采用方案**

- 无需物理操作的永久广播和一键配对；
- 在 WebUI 手工填写 Windows IPv4、端口和令牌；
- USB 串口作为日常配对方式；
- 用户长期管理固定 PIN。

**影响**

- 配对具有可见的物理授权边界；
- 普通用户无需理解端口和设备令牌；
- 发现、旧码宽限、配对成功和清除关系必须保持双方状态一致。

**复审条件**
引入可信账号体系、二维码扫描、系统级发现协议，或多设备场景使当前流程明显不足。

## DEC-006：内部设备令牌自动管理

**状态：已采用**

**背景**
指标、显示控制、远程重启和 OTA 需要局域网鉴权，但长令牌不适合作为普通用户配置项。

**决定**
使用 64 个十六进制字符表示 32 字节、256 位随机令牌。令牌由配对流程自动生成、同步和保存，请求通过 Bearer 头携带，比较使用恒定时间逻辑；普通界面和诊断信息不显示完整令牌。

**未采用方案**

- 完全取消 Device API 鉴权；
- 用户手工输入或复制令牌；
- 把 6 位配对码直接作为长期令牌；
- 在当前家庭局域网版本中增加账号或证书系统。

**影响**

- 长期控制接口与短期配对码职责分离；
- 清除 PC 配对只撤销 PC 本地信任；设备恢复默认设置会同时撤销设备端关系；
- 当前 HTTP 无 TLS，令牌不能防御局域网抓包，不应把接口暴露到公网。

**复审条件**
设备需要跨公网访问、运行在不可信网络或需要多人权限管理。

## DEC-007：AP 配网与 STA WebUI 复用同一配置实现

**状态：已采用**

**背景**
设备首次联网需要 captive portal；联网后也需要在没有 USB 的情况下更换 Wi-Fi。

**决定**
使用 ESP-IDF Wi-Fi、HTTP Server、NVS 和轻量通配 DNS。AP 模式地址固定为 `192.168.0.1`，STA 模式在设备局域网 IP 的 80 端口开放同一管理页；两者复用扫描、校验、双槽 NVS 保存和运行时重连逻辑。

**未采用方案**

- 为 AP 和 STA 编写两套配置页面与保存逻辑；
- 只允许串口配置；
- 普通 Wi-Fi 短暂掉线时自动开放 AP；
- 引入外部 Web 框架或文件系统。

**影响**

- 配网页面是确定性 gzip 单页，固件没有文件系统分区；
- STA WebUI 按用户确认的家庭可信局域网边界开放，修改 Wi-Fi 和恢复设备默认设置只使用页面内二次确认；
- 不得把设备 HTTP 端口暴露到公网或访客网络。

**复审条件**
部署环境不再可信、需要公网管理，或 WebUI 功能增长到单页内嵌资源难以维护。

## DEC-008：DHT11 由 ESP32 本地采集

**状态：已采用**

**背景**
DHT11 直接连接 GPIO47，温湿度不需要经过 PC。

**决定**
固件每 2 秒本地读取 DHT11，执行基于实测点的近似校准，并把结果写入环境状态。读取失败只清除温湿度 availability。

**未采用方案**

- 由 PC 轮询或代采 DHT11；
- 把本地传感器数据绕回 PC 再返回副屏；
- 读取失败时清除整个环境或指标快照。

**影响**

- PC 离线时仍可读取室内环境；
- 单点近似校准不是实验室标定，更换传感器后需要重新测量；
- DHT11 失败不得影响 Wi-Fi、天气、PC 或 Codex 数据。

**复审条件**
更换传感器型号，或需要可追溯的多点标定精度。

## DEC-009：Codex 指标来自本机会话和第一方 App Server

**状态：已采用，存在兼容风险**

**背景**
需要最后活动项目、模型、推理强度、上下文、双周额度和账户累计 Token；当前没有面向该副屏场景的稳定公开单一接口。

**决定**
任务上下文和额度从本机 Codex 会话 JSONL 增量解析，排除子代理并选择最后活动主任务；账户累计 Token 复用已登录的第一方 `codex.exe app-server --stdio` 的 `account/usage/read`。

**未采用方案**

- 读取屏幕文字或自动化点击 Codex UI；
- 读取认证文件并自行请求内部服务；
- 把最后一条 JSONL 简单当作当前项目；
- 用单个任务累计值冒充账户累计 Token。

**影响**

- 不复制登录凭据，也不依赖 Codex 窗口是否打开；
- JSONL 和 App Server 都是可能变化的内部边界，必须保留兼容解析、错误分类和回归样本；
- Codex 长时间没有新上下文事件时显示“不活跃”，而不是“离线”。

**复审条件**
OpenAI 提供稳定公开的本地使用量 API，或现有内部格式发生不兼容变化。

## DEC-010：天气使用和风天气 API Key

**状态：已采用**

**背景**
需要中国大陆可用的地点、天气、温度范围、风向、风力和图标数据。

**决定**
PC 使用用户提供的和风天气 API Host 和 API Key；中国大陆坐标按 GCJ-02，其他地区按 WGS84。API Key 使用当前 Windows 用户保护机制保存，测试与保存分离。

**未采用方案**

- JWT 作为当前首版认证方式；
- 自动猜测或静默转换用户坐标；
- 把 API Key 写入固件；
- 由 ESP32 直接访问天气服务。

**影响**

- PC 集中管理认证、重试和最近有效值；
- 用户需要在控制台配置 Host、Key、地点和坐标；
- 服务端认证错误与短期网络错误使用不同通知策略。

**复审条件**
和风天气接口、授权模式或许可条件变化，或出现更适合目标地区的服务。

## DEC-011：固件使用双 OTA 槽和 Bootloader 回滚

**状态：已采用**

**背景**
副屏未来主要只接供电，不能要求每次升级都使用 USB 和 GPIO0。

**决定**
8 MiB Flash 使用两个 `0x3E0000` OTA 应用槽；PC 校验本地固件并二次确认后，通过局域网上传到非运行槽。新固件运行至少 30 秒且网络链路可用后才确认有效，否则由 ESP-IDF Bootloader 回滚。

**未采用方案**

- 保持单 `factory` 分区并长期依赖串口；
- 覆盖当前运行槽；
- 无镜像校验、无用户确认的自动升级；
- 自行实现 Bootloader 或回滚机制。

**影响**

- 日常升级不再需要 GPIO0，传输中断和不可启动镜像不会破坏当前可用槽；
- 单个应用镜像必须小于 4,063,232 字节；
- 固件只接受用户手工选择的本地文件，不承担在线 Release 检查、下载和更新服务。

**复审条件**
固件超过槽容量、需要文件系统，或产品发布策略要求差分升级。

## DEC-012：PC 端开发便携、稳定版再提供安装包

**状态：已采用**

**背景**
开发阶段频繁替换程序并保留当前用户配置，稳定发布后仍希望有标准安装体验。

**决定**
开发阶段使用 `tools/Publish-PC.ps1` 生成解压即用的便携目录；用户配置保存在 `%LocalAppData%\SolisMonitor`，不跟随程序目录删除。稳定版同时提供由 `tools/Build-Installer.ps1` 生成的安装包，覆盖升级必须保留用户配置。

**未采用方案**

- 开发阶段每次生成安装包；
- 把配置放在便携程序目录；
- 静默覆盖安装新版本；
- 只提供源码构建。

**影响**

- 开发迭代和回退简单；
- 覆盖便携发布目录前必须先退出运行中的程序；
- PC 程序不提供 GitHub Release 在线检查、下载或自动更新。

**复审条件**
需要签名安装、多用户部署或更换安装技术。

## DEC-013：管理员主程序与非管理员通知助手分离

**状态：已采用**

**背景**
读取部分硬件传感器需要管理员权限，而提升权限的进程无法可靠直接发送 Windows 11 通知中心消息。

**决定**
主程序继续以管理员权限运行；发布目录携带独立的 `NotificationHost`，主程序通过当前用户的 Explorer 令牌启动非管理员助手发送通知。通知激活通过当前会话命名事件唤醒已运行主程序并打开服务页。

**未采用方案**

- 放弃管理员权限；
- 只使用旧式托盘气泡；
- 为通知引入常驻 Windows 服务或新网络端口；
- 让通知助手持有设备令牌或 API Key。

**影响**

- Windows 11 通知中心可用，同时维持硬件访问能力；
- 发布检查必须验证通知助手及依赖齐全；
- 助手只接收标题和正文，不得接收敏感配置。

**复审条件**
主程序不再需要提升权限，或 Windows 提供适合提升权限桌面应用的可靠通知通道。

## DEC-014：文档按稳定事实、任务和过程分层

**状态：已采用**

**背景**
项目长期迭代后，需求、设计、任务状态和踩坑记录曾混在一起，容易产生路径漂移和过时结论。

**决定**
根目录只保留用户入口和项目级事实：`README.md`、`DESIGN.md`、`TODO.md`，以及被 Git 忽略的本地 `DEVLOG.md`。专题事实放在 `docs/`；`TODO.md` 只维护当前任务、阻塞和验收条件，已完成过程由 Git 历史保存，`DEVLOG.md` 记录本地演进和踩坑。

**未采用方案**

- 在 README 中维护全部设计和任务；
- 在多个专题文档重复维护完成状态；
- 为每个小决定建立独立 ADR 文件；
- 提交包含本地路径和调试过程的 DEVLOG。

**影响**

- 文档入口和职责更清晰；
- 代码或协议行为改变时必须同步更新对应专题文档和 TODO；
- 本文件集中记录重大决策，避免当前规模下产生大量空壳 ADR。

**复审条件**
项目参与者和决策数量明显增加，单文件难以检索或需要正式审批流程。

## DEC-015：产品主程序只支持 .NET 10 x64

**状态：已采用**

**背景**
正式发布、安装器、通知助手、桌面冒烟测试和实机运行均固定为 `.NET 10 x64`，但主
程序项目仍声明 .NET Framework 4.7.2、x86 和 ARM64，形成没有发布证据的维护矩阵。

**决定**
Solis Monitor 主程序只声明 `net10.0-windows`、`x64` 和 `win-x64`。上游
`Aga.Controls` 保留 `net472`，`LibreHardwareMonitorLib` 保留其多目标框架和多架构
声明；产品发布只消费它们满足 `.NET 10 x64` 主程序所需的输出。

**未采用方案**

- 继续把主程序的 .NET Framework 4.7.2、x86 和 ARM64 视为受支持产品；
- 同时把 `Aga.Controls` 移植到 .NET 10；
- 为了产品发布而删除 `LibreHardwareMonitorLib` 的上游构建矩阵。

**影响**

- 产品支持范围与实际发布和验证范围一致；
- 主程序构建、恢复和条件配置更简单；
- 不承诺 x86、ARM64 或 .NET Framework 主程序兼容性；
- 上游控件和硬件库仍可保持较小同步差异。

**复审条件**
需要发布 ARM64/x86 安装包、重新支持旧 Windows，或上游控件正式提供现代 .NET 目标。
